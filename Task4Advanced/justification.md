# Обоснование событийного подхода для системы "Будущее 2.0"

## Текущая ситуация: Проблемы с Camel и DWH

### Архитектурные ограничения текущей системы

Существующая архитектура «Будущего 2.0» построена на базе двух ключевых компонентов интеграции:

1. **DWH на SQL Server 2008** — центральное хранилище, содержащее всю бизнес-логику и данные
2. **ESB на Apache Camel** — шина для синхронной и квазисинхронной интеграции систем

Эта архитектура порождает ряд критических проблем:

#### Проблема 1: Монолитное DWH — единая точка отказа и узкое место
- Все системы (финтех, ИИ, BI) зависят от одного DWH
- Любые изменения схемы DWH требуют согласования и тестирования всех зависимых систем
- Формирование сложных отчётов занимает часы из-за огромного объёма (сотни терабайт) и сложности трансформаций
- Горизонтальное масштабирование DWH крайне ограничено в on-premise режиме

#### Проблема 2: Apache Camel — жёсткие синхронные связи
- Camel реализует в основном синхронные и request-reply интеграции
- При добавлении нового бизнес-направления (фармацевтика, оборудование) необходимо переписывать маршруты Camel
- Отсутствие единого каталога схем данных приводит к несовместимости форматов
- Трудно масштабировать: узкое место при пиковых нагрузках

#### Проблема 3: Невозможность масштабирования на новые домены
- Подключение каждого нового домена требует значительных изменений в DWH и маршрутах Camel
- Бизнес-логика «закапывается» в DWH, ухудшая читаемость и поддерживаемость
- Time-to-market новых аналитических решений исчисляется месяцами

#### Проблема 4: Отсутствие near-real-time аналитики
- Пакетная обработка данных делает невозможной оперативную аналитику
- Данные в BI обновляются с задержкой (часы или сутки)
- Реакция на бизнес-события запаздывает

## Событийный подход: Ключевые преимущества

### 1. Слабая связанность (Loose Coupling)

**Что меняется:**
- Домены не вызывают друг друга напрямую — они публикуют события
- Добавление нового подписчика не требует изменений в источнике события
- Фармацевтические компании и производители оборудования подключаются как новые потребители событий без изменения медицинских или финансовых сервисов

**Пример:**
> При текущей архитектуре: добавление нового финтех-сервиса требует изменения маршрутов Camel и схемы DWH.
> При событийной архитектуре: новый сервис просто подписывается на нужные топики Kafka — изменений в существующих системах не нужно.

### 2. Масштабируемость

**Что меняется:**
- Kafka горизонтально масштабируется независимо от других компонентов
- Каждый домен имеет изолированную БД (PostgreSQL) вместо единого DWH
- Потоковые витрины (Apache Flink) обрабатывают миллионы событий в секунду
- Data Lake (Apache Iceberg) принимает данные из неограниченного количества источников

**Количественный эффект:**
- Throughput Kafka: > 100,000 событий/сек при необходимом масштабировании
- Latency потоковых витрин: < 1 минуты vs часы у текущих batch-отчётов
- Количество доменов: не ограничено, каждый добавляется независимо

### 3. Гибкость и скорость реакции

**Что меняется:**
- Время создания нового отчёта сокращается с дней до часов благодаря Self-service BI
- Новые бизнес-направления интегрируются через стандартный контракт события, а не через кастомные маршруты Camel
- Изменение схемы событий управляется через Schema Registry с контролем обратной совместимости

**Пример:**
> При добавлении нового финансового продукта (страховой полис): достаточно создать новый сервис с новыми топиками Kafka, не затрагивая существующие медицинские или финтех-домены.

### 4. Переход к near-real-time аналитике

**Что меняется:**
- Потоковые витрины агрегируют события в реальном времени
- Метрики обновляются с задержкой < 1 минуты вместо часовой пакетной обработки
- Бизнес-пользователи видят актуальные KPI без ожидания ночного ETL

### 5. Надёжность и отказоустойчивость

**Что меняется:**
- Kafka обеспечивает persistent хранение событий и возможность replay
- Dead Letter Queue (DLQ) изолирует неуспешные сообщения без остановки обработки
- Паттерн Saga управляет распределёнными транзакциями между доменами с компенсацией
- Circuit Breaker предотвращает каскадные сбои

**Пример:**
> При отказе финтех-сервиса: сообщения накапливаются в Kafka и обрабатываются после восстановления без потери данных. В текущей архитектуре с синхронным Camel — сбой одного сервиса блокирует цепочку вызовов.

### 6. Поддержка регуляторных требований

**Что меняется:**
- Полный аудит-лог всех событий хранится в Kafka и Data Lake (immutable)
- Медицинские данные остаются изолированными — в аналитические витрины не включаются медицинские карты и результаты исследований (это соответствует требованию задания)
- Шифрование событий при передаче и хранении
- Географические ограничения на хранение данных через региональные кластеры Kafka

## Сравнительный анализ

| Критерий                        | Текущий подход (Camel + DWH)    | Событийная архитектура (Kafka)       |
|---------------------------------|----------------------------------|---------------------------------------|
| Связанность доменов             | Высокая (жёсткие интеграции)    | Низкая (через события)                |
| Масштабируемость                | Ограниченная (on-premise DWH)   | Горизонтальная, неограниченная        |
| Добавление нового домена        | Месяцы (изменение DWH + Camel)  | Недели (подписка на топики)           |
| Latency аналитики               | Часы (batch ETL)                 | Секунды–минуты (потоки)               |
| Отказоустойчивость              | Низкая (синхронные вызовы)      | Высокая (DLQ, replay, saga)           |
| Аудит и соответствие нормам     | Сложно (логи в DWH)             | Встроен (immutable event log)         |
| Time-to-market новых отчётов    | Дни–недели                       | Часы (Self-service BI)                |
| Геораспределённость             | Сложна (один DWH)               | Нативна (региональные кластеры Kafka) |

## Стратегия перехода

Прямой отказ от Camel и DWH невозможен и опасен. Предлагается постепенный переход через Strangler Fig Pattern:

1. **Фаза 1 (0–6 мес.)**: Антикоррупционный слой читает из DWH/Camel и публикует события в Kafka. Новые домены начинают работать в событийной архитектуре.

2. **Фаза 2 (6–18 мес.)**: Критические домены переводятся на собственные БД. Camel используется только как мост совместимости. Запускаются потоковые витрины.

3. **Фаза 3 (18–36 мес.)**: Полный отказ от синхронных интеграций на критическом пути. DWH переходит в режим архивного хранилища. Camel постепенно выводится из эксплуатации.

## Выводы

Событийный подход через Apache Kafka — это не просто технологическая замена, а архитектурный сдвиг, который позволит «Будущему 2.0»:

1. **Расти без трения**: каждое новое бизнес-направление подключается как независимый домен
2. **Реагировать быстрее**: near-real-time аналитика вместо дневных batch-отчётов
3. **Снизить риски**: изолированные домены не тянут друг друга при сбоях
4. **Соответствовать регуляторам**: встроенный аудит-лог и изоляция медицинских данных
5. **Масштабироваться географически**: региональные кластеры без перестройки архитектуры

Текущая архитектура на Camel и DWH достигла своего предела масштабируемости. Событийная архитектура — это инвестиция в следующие 5–10 лет роста компании.
